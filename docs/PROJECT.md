# Документация проекта «Бок о бок»

Актуально для исходного кода на 15 октября 2026 года. Рабочий сайт: [bokobok.pro](https://bokobok.pro/). Этот документ описывает возможности, устройство и типовые операции с сервисом. Фактическое состояние рабочей базы и версия на сервере проверяются отдельно.

## Назначение

«Бок о бок» — платформа для показа развития научных и технологических проектов. Основатель ведёт карточку проекта и дерево этапов с датами, уровнем готовности технологии (УГТ), результатами и материалами. Сотрудник фонда проверяет изменения и публикует версии. Инвестор изучает опубликованные проекты, сравнивает их и задаёт вопросы. Главный администратор управляет доступом и контролирует работу системы.

Гость может открыть главную страницу и ознакомительный просмотр платформы без регистрации. Рабочие кабинеты и материалы проектов требуют соответствующего доступа.

## Роли и доступ

| Роль | Основные действия |
| --- | --- |
| Основатель | Подать заявку, после одобрения создать проект, редактировать рабочую версию, добавлять этапы и материалы, отправлять на проверку, подводить итог события. |
| Сотрудник фонда | Работать с назначенными проектами, проверять версии, публиковать их или возвращать на доработку, отвечать на вопросы. |
| Инвестор | Просматривать опубликованные проекты, сравнивать их, отслеживать обновления и задавать вопросы. |
| Главный администратор | Управлять пользователями и заявками, назначать сотрудников фонда, создавать приглашения инвесторам, просматривать аудит, логи и состояние системы. |

Внутри команды проекта могут быть участники с доступом на редактирование (`researcher`) или просмотр (`viewer`). Основатель регистрируется через заявку; инвестора и сотрудника фонда создаёт администратор. Отдельный механизм QR-приглашений выдаёт каждому новому браузеру собственный кабинет инвестора без регистрационной формы.

## Жизненный цикл проекта

1. Основатель заполняет карточку: код, название, описание, область, регион и текущий УГТ.
2. В дереве добавляет любое число этапов, задаёт родительские связи, даты, статусы, критерии и ответственных. Граф показывает ветвления и результаты; карту можно масштабировать и развернуть.
3. К этапу прикладывает документы, фото или видео размером до 50 МБ за файл. Доступ к файлам проверяется сервером. На странице события фото отображаются галереей, видео — встроенным плеером.
4. Отправляет рабочую версию на проверку. Во время проверки она не редактируется.
5. Сотрудник фонда публикует версию либо возвращает её с замечаниями. Инвесторы видят последнюю опубликованную версию; незавершённые изменения им не показываются.
6. Следующие изменения ведутся в новой рабочей версии. История сохраняет публикации и действия; авторизованные участники получают уведомления по своим правам.

У события есть отдельная страница с описанием, сроком, УГТ, критериями, материалами и итогом. Основатель может зафиксировать итог как «успешно», «неуспешно» или «неопределённо» с обоснованием.

## Основные страницы

- `index.html` — главная страница, вход, регистрация и рабочее пространство.
- `preview.html` — ознакомительный просмотр без входа.
- `admin.html` — кабинет главного администратора.
- Страница проекта — дерево, временная шкала, УГТ, материалы, команда, история, описание и вопросы.
- Страница события — подробности выбранного этапа и его материалы.
- Сравнение проектов — сопоставление доступных пользователю проектов и событий.
- Сообщения, уведомления, изменения и личный кабинет — отдельные разделы авторизованного пользователя.

## Техническое устройство

Фронтенд написан на HTML, CSS и JavaScript без сборщика. `app.js` управляет входом и навигацией; `matrix28.js` — картой проекта и временной линзой; `workflow-ui.js` — формами и материалами; `event-page.js` — страницей события; `admin.js` — административным кабинетом.

Сервер — Python 3.12 на стандартной библиотеке. `backend/server.py` обслуживает HTTP, статические файлы и API; `backend/workflow.py` содержит правила доступа и операции с проектами; `backend/db.py` управляет SQLite и миграциями из `db/migrations/`. В Docker Compose приложение работает за Caddy, который принимает HTTP/HTTPS. Конфигурация: `compose.yaml`, `Dockerfile`, `deploy/Caddyfile`.

SQLite по умолчанию находится в `data/bokobok.db`, а загруженные файлы — в `data/uploads/`. В контейнере оба размещены в постоянном томе `/data`. Материалы небольшой величины могут храниться непосредственно в базе. Для полного восстановления нужны **и копия базы, и архив загрузок**.

API использует авторизацию Bearer-токеном. Ключевые маршруты: `GET /api/health`, `GET /api/projects`, `GET /api/projects/:id`, `GET /api/projects/comparison`, `GET /api/notifications`, `GET /api/messages/contacts` и административные маршруты `/api/admin/*`. Подробности см. в [описании архитектуры и API](architecture-api.md); при расхождении с ним ориентируйтесь на `backend/server.py` и `backend/workflow.py`.

## Локальный запуск и проверка

Из корня репозитория:

```bash
python3 -B backend/server.py 5188
```

Откройте `http://127.0.0.1:5188/`. При первом запуске миграции создадут пустую базу со справочниками. Они не создают пользователей или проекты автоматически. Для первого администратора используется команда:

```bash
python3 backend/create_admin.py --name 'Имя Фамилия' --email admin@example.ru --phone +79991234567
```

Пароль вводится в терминале скрыто. Не сохраняйте его в репозитории или документации. Проверка кода:

```bash
python3 -B -m unittest discover -s tests -q
node --check app.js
node --check workflow-ui.js
node --check matrix28.js
```

Тесты работают с временными базами. Для локальной SQLite можно задать другой путь через `BOKOBOK_DB_PATH`.

## Рабочий сервер и обновление

Текущая установка описана для `/opt/bokobok` на Cloud.ru и домена `bokobok.pro`. Состояние подключения, DNS и TLS проверяйте на самой ВМ. Обычный порядок обновления:

```bash
cd /opt/bokobok
sudo sh deploy/backup.sh
sudo git pull --ff-only origin main
sudo docker compose up -d --build
sudo docker compose ps
curl -fsS https://bokobok.pro/api/health
```

Успешный ответ health-check — `{"status":"ok","database":"ok"}`. Он подтверждает доступность API и БД, но не заменяет проверку затронутой функции в браузере. Скрипт резервирования создаёт проверенную копию SQLite и отдельный архив загрузок в `/opt/bokobok/backups/`; локальные копии хранятся 14 дней. Копии следует также переносить за пределы ВМ. Инструкции по восстановлению и таймеру резервирования находятся в [руководстве по эксплуатации](operations.md).

Команды `backend/seed_demo.py`, `backend/seed_roadmaps.py`, `backend/move_agct_media.py` и `backend/delete_project.py` меняют продуктовые данные **только при отдельном явном запуске**. Не запускайте их при обычном обновлении приложения. Перед операциями с рабочей базой создавайте резервную копию; скрипты с режимом предварительного просмотра сначала запускайте без `--apply`.

## Настройки и ограничения

Секреты задаются в `.env` на сервере и не коммитятся. Пример — `.env.example`. `DOMAIN` задаёт домен Caddy. `SMS_RU_API_ID` нужен для SMS-проверки; `BOKOBOK_DISABLE_SMS_2FA=1` временно отключает её. При отключённой SMS-проверке вход всё равно требует пароль. Используйте HTTPS для рабочего сайта.

Сервис не отправляет пользователям письма с учётными данными. Пароли не могут быть извлечены из базы в открытом виде; при утрате администратор задаёт новый. Резервное копирование, мониторинг, SMS-доставка и доступность сайта зависят от настроек сервера и должны проверяться отдельно от исходного кода.
